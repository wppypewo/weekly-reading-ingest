# 編碼代理的產出與品質落在不同指標上

## 核心結論

用來證明 AI 編碼代理有效的那個數字，和用來證明它有代價的那個數字，來自不同的測量系統，而且到 2026 年為止還沒有人把兩者放在同一個研究裡。

Microsoft 的 23 頁實地研究測到採用者的合併 PR 增加 24.0%（95% CI +14.5% 到 +33.7%），四個月不衰減。同一年一份 CMU 的因果研究測到採用代理的開源專案認知複雜度上升 34.85% 到 42.87%，靜態分析警告上升 17.73% 到 19.00%。前者的產出指標完全不含品質，後者的品質指標完全不含個人產出。兩份研究都做得認真，結論卻無法互相驗證，因為它們量的根本不是同一件事。

Microsoft 那篇的作者在結論裡自己承認了這件事：「The pressing open question is now about quality, whether this added throughput yields better software. The field still lacks agreed-upon measures to answer it.」花二十三頁證明產出變多，最後一句話說真正該問的是品質，而這個領域還沒有能回答的共識指標。

## 背後原因 / 機制

### 產出的那一半是怎麼測出來的

Microsoft 研究的產出定義是「28 天內完成合併的 pull request 數」。這個定義本身是為了避免右截斷偏誤（長期未合併的 PR 會被錯算成零），代價是排除了所有需要更久審查的變更。

他們用了兩套彼此獨立的設計來測它。

第一套是 CausalImpact，一種貝葉斯結構時間序列方法。處理組是 2026 年 1 月 5 日到 3 月間開始使用工具的工程師，對照的合成反事實由十組未使用任何工具的 PR 創作者的日均值建構。Pre 期長達 461 天（2024-10-01 到 2026-01-04），Post 期 115 天。結果是每工程師每日合併 PR 提升 24.0%，p<0.001。

作者做了一項安慰劑檢定：把介入日假設成 2025 年 10 月 6 日（真實推行前三個月），重跑同一套模型，得到 −1.1%，95% CI [−10.6%, +8.6%]，跨過零。這排除了「效果來自時序趨勢或季節性」的解釋，但它排除不了選擇偏誤，因為處理組始終是自願採用者。

作者也把 Post 期切開來看衰減。2 月是 +29.4% [+17.7%, +44.4%]，3 到 4 月是 +20.0% [+7.4%, +35.9%]。點估計下降了，但兩個區間大幅重疊，不構成統計顯著的衰減。這個結果被作者拿來對照 He 等人的 Cursor 研究，那份研究發現效果在第二個月褪去、第三個月消失，而該時間跨度落在本研究的四個月觀察窗內。

第二套設計換了識別策略。它只看使用者內部（within-person），用工程師固定效應加週固定效應的泊松迴歸，把每週的工具使用天數分成 0 到 5+ 六組，看同一個人在高使用週與低使用週的 PR 數差異。每週用 1 天對應 +15.0%，每週用 5 天以上對應 +50.1%，曲線單調遞增。

作者對第二套設計的自我評價很克制：高使用週可能本來就含有較輕的任務組合，因此劑量反應應該當成關聯而非因果看。這句話比它看起來重要，因為它意味著 +50.1% 這個數字裡有一部分是「這週的活比較好做，所以我既多用了工具也多交了 PR」。

### 採用與留存由不同機制驅動

採用研究的兩個問題給出了符號相反的答案，這是全篇最沒被展開卻最耐人尋味的地方。

RQ1 問誰會先去試。答案壓倒性地是社會因素。跳級同儕（向同一位經理的經理報告的那群人）中有 25% 以上在用，該工程師嘗試的勝率上升 216%，是全篇最大的效果量。直屬經理在用，上升 82%。負責 code review 的同儕中 25% 以上在用，上升 54%。相比之下職級的效果小得多：IC5 是 +22%，IC2 與 IC3 是 −13% 與 −14%，經理職級 M4 到 M6 沒有顯著差異。年資除了「到職未滿一年」的 +11%，其餘都不顯著。

先前的 IDE Copilot 使用也強力預測嘗試。用過 60 天以上者勝率 +83%，用過 1 到 14 天者 +49%。

RQ2 問誰會留下來，留存定義是首次使用後 14 天內至少有 5 天活動。社會因素依然有效但弱化了：跳級同儕 25%+ 對應 +66%，評論同儕 +54%，直屬經理只剩 +22%。真正翻轉的是 IDE Copilot 這一項，它從 +83% 變成全分層一律 −12% 到 −15%。用過 IDE Copilot 的人更會去試 CLI 代理，試了之後反而更容易不再用。

同時，基線 PR 活動在留存上取代了社會曝露的位置。每週 2 個以上 PR 的工程師留存勝率 +31%，是留存模型中最強的行為預測因子。

作者對這個翻轉只給了一句推測：這些人有替代選項。沒有進一步的分析，也沒有追蹤這些人後來去了哪裡。他們在 Discussion 裡把整組發現總結成「What an engineer does (peer ties, prior tool use, PR cadence) explains who adopts and retains far better than who an engineer is in the organization」，行為比身分更能解釋採用與留存。這個總結是對的，但它掩蓋了同一個行為變數在兩個階段符號相反這件事。

### 工具比較與作者自己的位置

RQ4 比較兩個工具在單工具使用者身上的效果。Claude Code 是 +11.4% [+9.4%, +13.6%]，Copilot CLI 是 +24.9% [+23.0%, +26.8%]，差距 2.2 倍，p<0.0001。

作者對這個結果的處理值得記下來。他們主動指出這個方向與公眾觀感相反（「despite public perception favoring Claude Code for autonomous work」），列了兩個假說：兩個工具被用在不同的任務組合上；Microsoft 擁有 GitHub 帶來的組織整合優勢。兩個假說都沒有檢驗。

同一篇論文的位置性聲明寫著：三位作者皆為 Microsoft 員工，Microsoft 銷售 AI 工具、鼓勵員工使用、並擁有 GitHub。作者稱沒有受到明確壓力，但承認「鄰近性可能形塑研究問題、設計與詮釋」。他們沒有提出任何緩解措施，例如預先註冊分析計畫、外部共同作者、或把工具名稱在分析階段盲化。

這不表示 2.2 倍是假的。它表示這個特定數字是全篇最不該被單獨摘出來引用的一個。

還有一層：作者披露初稿與第 4、5 節的全部分析程式碼由 GitHub Copilot（Claude Opus 4.6 到 4.8）產出。一篇評估 AI 編碼工具效果的論文，其分析程式碼由 AI 編碼工具寫成，而該論文的核心限制正是「我們沒測品質」。

### 質性回應動搖了計數的可比性

609 份 Agentic Engineering Day 開放式問卷回應被歸成五個主題。其中一個主題直接威脅到量化部分的識別假設。

有工程師表示他們開始接手「larger changes that I never would have taken on in the past」，以前不會碰的大型變更。另一位描述某次變更中「nearly 100% of the code written by Copilot CLI agent」。其他人提到工具讓他們去做文件更新、品質分析、原型開發，以及平行推進多條工作流。

如果任務組合真的改變了，那麼「合併 PR 數」在採用前後就不是同一個單位。一個涵蓋更大變更的 PR 與一個修 typo 的 PR 在計數上等值。作者在限制章節列出的三項代理指標缺陷之一正是「可能偏好小而頻繁的 PR」，但質性資料指向的是相反方向的變化。兩者都可能同時發生，而計數看不出來。

### 品質的那一半在另一份研究裡

Agarwal、He 與 Vasilescu 的 CMU 研究（arXiv 2601.13597v2）處理的是同一個技術對象，設計卻完全不同。單位是開源倉庫而非個人，資料是 AIDev v3，涵蓋 2024 年 1 月到 2025 年 11 月，517 個處理倉庫對 679 個匹配控制倉庫。匹配用傾向分數（羅吉斯迴歸，AUC 0.92 到 0.99，1:3 配對，要求語言相同），因果識別用錯開採用的差異中差異，估計器是 Borusyak 等人的插補法，事件研究從 t=−2 到 t=+6 月。

關鍵在於他們把樣本分成兩類。Agent-First 是代理為第一個引入的 AI 工具（401 個處理倉庫），IDE-First 是先有 IDE 型 AI 助手再引入代理（117 個）。

速度結果：

| 指標 | Agent-First | IDE-First |
|---|---|---|
| 提交數 | +36.25%（β=0.309, SE=0.051, p<0.001） | +3.06%（β=0.030, SE=0.092, 不顯著） |
| 新增行數 | +76.59%（β=0.569, SE=0.103, p<0.001） | −6.34%（β=−0.066, SE=0.189, 不顯著） |

品質結果：

| 指標 | Agent-First | IDE-First |
|---|---|---|
| 靜態分析警告 | +17.73%（p<0.001） | +19.00%（不顯著，SE=0.114） |
| 認知複雜度 | +34.85%（p<0.001） | +42.87%（p<0.01） |
| 重複行密度 | +7.92%（邊界） | −0.94%（不顯著） |
| 註釋行密度 | +4.34%（不顯著） | +22.30%（p<0.001） |

動態效果更尖銳。Agent-First 在 t=0 達到高峰（提交 +111%，新增行 +216%），之後穩定在 +49% 到 +109% 區間。IDE-First 只在 t=0 到 t=2 有 +16% 到 +28% 的短暫提交增長，t=6 時掉到約 −35% 提交與 −61% 新增行。複雜度在兩組都持續上升，Agent-First 從 t=0 的 +20.7% 爬到 t=5 的約 +49%。

把兩份研究並置：速度紅利集中在沒有 AI 使用經驗的專案，複雜度成本兩組都付。而 Microsoft 研究的樣本恰好以 IDE Copilot 使用者為主體（RQ1 顯示他們是最積極的嘗試者），也就是 CMU 定義下的 IDE-First 群體，那群在 CMU 研究裡速度效果不顯著、複雜度上升 42.87% 的人。

這兩個結論不必然矛盾。單位不同（個人 vs 倉庫）、環境不同（企業內部 vs 開源）、時間不同（2026 年初 vs 2024–2025）、工具世代不同。但它們也無法互相支持，因為沒有任何一項指標是共通的。

CMU 那份自己的限制同樣不輕：作者承認靜態分析警告與複雜度存在孤立的預處理係數，平行趨勢可能不完全滿足；無法測量使用強度；估計應視為意圖治療效應而非完整因果證據。

### 為什麼這是一個結構問題而不是暫時的資料缺口

三個原因讓兩半不容易合起來。

測量成本不對稱。合併 PR 數可以從版本控制系統直接讀出，靜態分析警告與認知複雜度需要對每個版本跑分析工具，而「這段程式碼六個月後有沒有出事」需要等六個月。組織能拿到的即時指標天然偏向產出那一側。

歸屬單位不同。產出屬於個人，品質屬於程式碼庫。個人層級的遙測看不到程式碼庫層級的劣化，倉庫層級的分析看不到誰交了多少東西。要把兩者接起來，需要把每一行變更歸屬到具體的人與具體的工具使用，而 CMU 那份自己承認歸屬有誤差。

利益結構不對稱。做產出研究的機構通常也是賣工具或用工具的機構，Microsoft 這篇是明例。做品質研究的多半是學術軟工社群，而他們拿不到企業內部的個人層級遙測。兩邊各自有能力做的那一半，正好是對自己有利或至少無害的那一半。

## 使用場景

判斷任何一份 AI 編碼工具效果宣稱時，先問它量的是哪一側。看到「提升 X%」，接著問三個問題：X 是什麼單位（PR 數、提交數、任務完成時間），有沒有任何品質指標，樣本是不是自願採用者。三個問題有兩個答不出來，這個數字只能當成該工具「被用得多」的證據，不能當成「有用」的證據。

評估自己的使用時，記住 Microsoft 那份的劑量反應曲線是關聯而非因果。自己感覺到的「用得多的那週產出也多」，有一部分是那週的活本來就好做。要分辨，需要把任務難度先記下來再看產出，而不是事後回想。

如果決定引入代理工具而在意程式碼長期健康，CMU 那份給的操作性含意是：先量基線的複雜度與靜態分析警告，因為這兩項在他們的資料裡是持續上升而非一次性跳升，t=0 的 +20.7% 到 t=5 的 +49% 這條曲線只有在有基線的情況下才看得出來。

## 容易混淆 / 常見陷阱

把 +24% 當成「AI 讓人快 24%」。它是每工程師每日合併 PR 數的變化，不是速度、不是完成任務數、不是程式碼量。

把 Copilot CLI 勝 Claude Code 2.2 倍當成工具能力排名。這個數字來自 Microsoft 員工研究 Microsoft 環境中的 Microsoft 產品，作者自己指出方向與公眾觀感相反，並列了兩個未經檢驗的替代解釋。

把「四個月不衰減」當成「長期有效」。作者明說 16 週足以捕捉早期衰減但無法檢測長期衰減。He 等人的 Cursor 研究在第三個月觀察到效果消失，落在同一個窗口內，兩者的差異目前無解。

把社會擴散的 +216% 套到個人身上。那是大型組織內部的傳播機制，對沒有同儕與經理的個人開發者不成立。

把 CMU 的複雜度上升直接讀成「AI 寫的程式碼比較爛」。認知複雜度是結構指標，它會因為專案接手了更大的變更而上升，這與質性資料中「開始接手以前不會碰的大型變更」是一致的。複雜度上升是事實，成因未定。

把兩份研究讀成「一個說好一個說壞」。它們沒有共同指標，構不成對立命題。正確的讀法是各自量到了一半，而合起來的那個完整答案目前不存在。

## 與我目前專案 / 投資 / 學習的關係

本週沒有明確的專案連結。現有五個專案中四個處於維護或完結狀態，personal-website 尚未初始化，沒有一個以 AI 工作流本身為研究對象。

與學習路徑的關係在方法論那一層。這篇補的是同一條線的第三個場域：[[wiki/concepts/ai-engineering/llm-judge-self-inconsistency]] 講評分者本身不穩定，[[wiki/concepts/ai-engineering/harness-induced-belief-divergence]] 講執行環境不中立，本篇講的是測量的覆蓋範圍不完整。前兩者的問題是「測得不準」，本篇的問題是「只測了一半，而且那一半剛好是好看的一半」。

## 未確認 / 待查證

He 等人的 Cursor 合成控制研究只透過 Microsoft 論文的 Related Work 轉述得知（效果第二個月褪去、第三個月消失），**未回溯原始文獻**，未取得其樣本規模、指標定義與確切數值。

Microsoft 論文的 RQ1 與 RQ2 完整迴歸係數以圖表呈現，本次取得的是文字敘述中的點估計與部分信賴區間，未取得完整的係數表與各分層的標準誤。

Microsoft 論文的總樣本數（工程師人數、採用者人數）在可取得的 HTML 內容中未明確列出。

CMU 研究中 IDE-First 組僅 117 個處理倉庫對 73 個控制倉庫，多項品質係數的標準誤偏大（靜態分析警告 SE=0.114），該組的不顯著結果有多少是檢定力不足所致，未查證。

兩份研究都在 2026 年上半發表，尚無足夠後續引用可判斷學界如何處理它們之間的落差。
